LightInject or Microsoft DI

Microsoft.Extensions.DependencyInjection.Abstractions is already pinned at 10.0.10. This is what can sit behind it, what each option costs to keep, and the two disposal rules that matter more than the choice itself.

LightInject already implements the abstraction. The shim you were budgeting for is zero lines.

LightInject.Microsoft.DependencyInjection 4.1.0 passes Microsoft.Extensions.DependencyInjection.Specification.Tests — the same conformance suite Microsoft runs against its own container. So the question is no longer can I, it is should I.

And for a graph of services that all live for the lifetime of the app — Device, SwapChain, the asset pipeline — consumed only through IServiceCollection and IServiceProvider, the honest answer is that the built-in container gives you everything a richer one would. The abstraction is a lowest common denominator: whatever makes LightInject nicer than ServiceProvider lives in LightInject's own API, which you would not be calling.

Start on the built-in container. Swap when you actually want decorators or assembly scanning — behind the abstraction that swap is one line at the composition root.

Two corrections to the premise

Exists

LightInject does implement the abstraction

seesharper/LightInject.Microsoft.DependencyInjection, version 4.1.0, published 2026-05-28. 2.8 million downloads across all versions. It targets net8.0 and netstandard2.0, so it loads fine on your net10.0, and it depends on Microsoft.Extensions.DependencyInjection.Abstractions ≥ 10.0.8 — which your Directory.Packages.props already satisfies at 10.0.10.

One gotcha in the README worth remembering if CapriKit ever grows a generic host: this package is the raw adapter. For a hosted app you are meant to use LightInject.Microsoft.Hosting instead, which wires IServiceProviderFactory into the host builder for you.

Not web

Microsoft.Extensions.DependencyInjection was never web-specific

The implementation package has zero ASP.NET dependencies and never has. The association is purely that ASP.NET is its largest consumer. It is a plain library you can reference from a WinExe.

The change you are half-remembering is most likely keyed services, added to the abstraction in .NET 8: AddKeyedSingleton, GetRequiredKeyedService, IKeyedServiceProvider. Useful here if you ever want two named SwapChains or a per-adapter Device. The LightInject adapter implements the keyed interfaces too, mapping service keys onto LightInject's string service names.

The options

Start here

Built-in Microsoft.Extensions.DependencyInjection

The reference implementation of the abstraction you are already coding against. One package, no third-party risk, no adapter layer that can lag a .NET release.

What it does not have, per Microsoft's own list of reasons to replace it: property injection, child containers, custom lifetime management, Func<T> for lazy initialization, and convention-based registration. Nothing on that list is load-bearing for a fixed set of engine singletons wired up by hand in one place.

Zero shim

LightInject + its official adapter

Two package references and one line at the composition root:

Directory.Packages.props

<PackageVersion Include="LightInject" Version="7.x" />
<PackageVersion Include="LightInject.Microsoft.DependencyInjection" Version="4.1.0" />

Composition root

// WithMicrosoftSettings() switches LightInject to MS DI semantics.
// Without it, conformance is not guaranteed.
var container = new ServiceContainer(ContainerOptions.Default.WithMicrosoftSettings());

var services = new ServiceCollection();
services.AddSingleton<Device>();
services.AddSingleton<SwapChain>();
// snip

IServiceProvider provider = container.CreateServiceProvider(services);

This buys you LightInject's decorators, Func<T>, property injection and assembly scanning — but only when you talk to IServiceContainer directly. Through IServiceCollection alone you get none of it.

Heavier

Autofac, DryIoc, Stashbox

All three ship first-party adapters and all three appear on Microsoft's supported-container list alongside LightInject, Lamar, Grace and Simple Injector. DryIoc and Stashbox are the fast ones; Autofac is the best documented and the heaviest.

None of them buy anything the built-in container lacks for a graph of app-lifetime singletons. Their strengths — module systems, interception, elaborate scoping — are answers to problems a game engine's composition root does not have.

Compile-time

Pure.DI, Jab — source-generated containers

Genuinely interesting for an engine: no reflection, NativeAOT-clean, and resolution compiles down to straight-line construction rather than a runtime graph walk. Jab reports ~200× faster startup and ~7× faster resolution than the built-in container.

The catch is the shape of registration. Pure.DI can meet you halfway — the Pure.DI.MS package has your composition class derive from ServiceProviderFactory<T>, so it can hand out an IServiceProvider. Jab explicitly will not: its stated plan is to support the minimum the abstraction requires but not IServiceCollection-based registration, because that is inherently runtime-based.

Either way you register through attributes on a partial class, not the IServiceCollection API. That is a different programming model, not a drop-in implementation of the abstraction. Worth revisiting only if NativeAOT becomes a goal.

Don't

A hand-rolled LightInject shim

Sized in the next section. The short version: the maintained one is 693 lines, and the last 10% of the semantics is where every bug lives.

The shim, sized

You asked how much you would have to keep alive if you wired LightInject to the abstraction yourself. The maintained adapter is a single source file:

693 lines in LightInject.Microsoft.DependencyInjection.cs — the whole adapter, including keyed-service and annotated-constructor support.

These are the contracts it has to satisfy:

  • IServiceProvider
  • ISupportRequiredService
  • IKeyedServiceProvider
  • IServiceProviderIsKeyedService
  • IServiceScope
  • IServiceScopeFactory
  • IServiceProviderFactory<IServiceContainer>
  • IDisposable
  • IAsyncDisposable
  • ILifetime
  • ICloneableLifeTime

Plus the translation of every ServiceDescriptor across the full matrix — type × instance × factory, against singleton × scoped × transient, each with a keyed variant.

The plumbing is not the hard part. These four are:

Ordering

Registering IFoo twice means GetService<IFoo>() must return the last registration, while GetServices<IFoo>() must return all of them in registration order. Most containers natively do neither.

Open generics

typeof(ILogger<>) registered once must resolve ILogger<Device> on demand, and must still obey the ordering rule above.

Scope ownership

Transient IDisposables are tracked by the scope that resolved them, not the one that registered them, and released when that scope dies. Getting this wrong is a leak that only shows up under load.

Disposal order

Reverse creation order, and DisposeAsync preferred over Dispose where both exist. For GPU objects, getting this backwards is a crash on shutdown, not a warning.

What actually matters here

“Everything is an app-lifetime singleton” means the features you would normally shop for — scoping, per-request lifetimes, captive-dependency validation — are close to irrelevant. What is not irrelevant, for Device and SwapChain, is disposal. Two rules bite, and they bite identically on every option above.

Trap 1

Reverse creation order, not registration order

Creation order is driven by resolution, not by the order you called AddSingleton. A lazily-touched Device can end up constructed after something that depends on it, and therefore disposed before it.

For GPU resources, don't lean on container disposal at all. Keep an explicit shutdown sequence and let the container own the lifetime, not the teardown order.

Trap 2

The container never disposes what it did not create

Straight from the .NET guidelines: for an instance registration, “the framework does not dispose of the services automatically. The developer is responsible for disposing the services.”

So the instance overload silently leaks native handles. Use the factory overload if you want the container to own cleanup.

Not disposed by the container

services.AddSingleton(new Device(adapter));  // you own Dispose()

Disposed by the container

services.AddSingleton<Device>(sp => new Device(adapter));

Related, and cheap to turn on either way: build with ValidateOnBuild and ValidateScopes so a mis-wired graph fails at startup naming the offending service, rather than at first resolve three frames into a render loop.

Recommended path

  1. 01
    now · one package

    Add Microsoft.Extensions.DependencyInjection to CapriKit.Tests.Tool

    Same version line as the abstractions you already pin. Wire the composition root by hand, use the factory overload for anything holding a native handle, and keep an explicit shutdown sequence for the graphics objects.

  2. 02
    when the registrations get repetitive

    Swap in LightInject

    One line changes at the composition root, because everything downstream only ever saw IServiceProvider. That is the whole payoff of coding against the abstraction — and it is why this decision is genuinely low-stakes today.

  3. 03
    only if NativeAOT becomes a goal

    Re-evaluate Pure.DI

    At that point the abstraction itself is the thing in the way, and the trade shifts from “which container” to “runtime graph or generated code”. A different question, worth its own note.
