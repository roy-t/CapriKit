Hosting a Game Loop

Dropping Serilog and LightInject leaves the generic host and the built-in container. That combination fits a tool better than it fits a game, and the seam between them is the thread that pumps messages.

Yes, it works, and the one decision that matters most is already right: the frame loop stays on the main thread and the host runs beside it.

Everything the last two rounds were about goes away. No container variable, no provider variable, no cast to IDisposable. The host owns the provider, disposes it in reverse creation order, and prefers the asynchronous path while doing it.

What you take on in exchange is a framework whose model is asynchronous, pool-threaded and configuration-driven, attached to a program that is none of those things. It never gets in the way, but it never carries the frame loop either. The honest framing is that the host is worth its weight for a tool that watches assets and recompiles shaders, and is mostly dead weight for a shipped game.

Keep it in CapriKit.Tests.Tool. Do not reach for it from a CapriKit library, and do not assume it is the right composition root for a game. The middle path below gives you startup validation and correct disposal without any of the hosting surface.

What the sketch is missing

Six things, ordered by how loudly they fail. The first two mean the sketch as written builds a graph that nothing constructs, against a window that does not exist yet.

Fatal

The window is never created

Win32Application.Initialize is what registers the window class, creates the handle, calls UpdateHandle and builds the event processors. The static Window property exists without it, but it carries no handle, and PumpMessages dereferences a null input processor on the first frame.

Registration order does not matter, because the registration captures the same object that UpdateHandle later mutates. Construction order does. Initialize before you resolve anything that reads the handle, which in practice means before Build.

Fatal

Nothing resolves the game loop

GameLoop is registered and never requested, so neither the device nor the swap chain is ever created. Ask for it between Build and the loop.

Silent

Startup validation is present but switched off

The default builder does configure it. CreateDefaultServiceProviderOptions reads IsDevelopment() and sets both ValidateScopes and ValidateOnBuild to that value. With DOTNET_ENVIRONMENT unset the environment is Production, so both land on false and you get nothing.

Either set the environment through HostApplicationBuilderSettings, or state the options yourself and stop depending on an ambient variable: 

builder.ConfigureContainer(new DefaultServiceProviderFactory(new ServiceProviderOptions
{
    ValidateOnBuild = true,
    ValidateScopes = true,
}));

That is the same seam a LightInjectServiceProviderFactory would occupy, which is exactly why plugging a third-party container in silently turned these options off before. The default factory is the only one that reads them.

Blocking

using should be await using

Host.Dispose is implemented as DisposeAsync().AsTask().GetAwaiter().GetResult(). Inside an async method that is a blocking wait for no reason. A windowed application installs no synchronization context so it will not deadlock, but the asynchronous form is free and is the one that reaches DisposeAsync on services that only implement it.

Cosmetic

Environment.GetCommandLineArgs includes the executable path

Index zero is the path to the executable, where the host expects the arguments a Main method receives. The command line configuration provider ignores an argument carrying no prefix and no equals sign rather than throwing, so this is silent rather than fatal. It is still the wrong array.

Design

Nothing connects the window to the host lifetime

There are now three ways the application can decide to stop, and only one of them is wired. Closing the window ends the loop. A console interrupt reaches ConsoleLifetime, which the default builder installs as the host lifetime on Windows. A background service that throws stops the host outright, because BackgroundServiceExceptionBehavior defaults to StopHost.

IHostApplicationLifetime is the one signal all three should meet at. Call StopApplication when the message pump reports a quit, and have the loop watch ApplicationStopping so a failed asset watcher does not leave you rendering into a half-dead process.

Two threading models, one process

This is the real subject. The host is built for programs whose work is asynchronous and runs on the thread pool, coordinated by IHostedService. A frame loop is one dedicated thread running at a fixed cadence, and a Win32 message pump must run on the thread that created the window handle. Those two models cannot be merged, only run side by side.

The host never owns the main thread. That is why Run and RunAsync are unusable here: both block the caller until the lifetime token trips, which is the one thing the frame loop cannot allow. Driving StartAsync and StopAsync by hand, as the sketch does, is the correct shape.

The consequence worth internalising is that the host contributes nothing to the middle column. It is a startup and shutdown concern with a background worker pool attached. Judge it on that, not on whether it is fast.

What you gain

  • Provider ownership, settled. The host disposes whatever the provider factory returned, probing IAsyncDisposable before IDisposable. Reverse creation order still holds, so the swap chain is released before the device.
  • Logging and options wiring. ILogger<T> becomes injectable without a hand-built factory, which matters because the asset pipeline registration already asks the container for ILoggerFactory. Typed settings arrive through IOptions<T>.
  • Layered configuration. Asset directories, output directories, resolution and adapter index stop being string literals in the composition root. For a test tool driven from a command line this is the most immediately useful thing on the list.
  • Background work with a real lifecycle. An asset watcher, a shader recompiler or a file mirror becomes an IHostedService that starts and stops with the application instead of a thread you remember to join. This is the strongest argument for the host in this specific project.
  • One shutdown signal. Window close, console interrupt and background failure all converge on IHostApplicationLifetime.
  • The container stays swappable. ConfigureContainer is the same seam that takes LightInject, so this is not a door you close.

What you pay

Weight

Roughly eight assemblies for a startup concern

Hosting drags in configuration, its file and environment providers, logging, options, file providers and diagnostics. Fine in an executable. Never acceptable in a CapriKit library, which should stay on the dependency injection abstractions alone.

Startup

File probing before the window appears

The default builder probes appsettings.json and its environment-specific sibling, reads user secrets in Development, scans environment variables and parses the command line. In Development it then walks the whole graph for ValidateOnBuild. Tens of milliseconds, which is invisible in a tool and visible in a game that should show something immediately.

Host.CreateEmptyApplicationBuilder skips all of it, including the console, debug, event source and Windows event log providers that a windowed executable with no standard output has no use for. If you go that route, remember to call AddLogging yourself, because the asset pipeline registration depends on it.

Reflection

Ahead-of-time compilation gets harder

Configuration binding and build-time validation both work by reflection. Native ahead-of-time compilation is reachable but needs the configuration source generator and care about what gets trimmed. If that ever becomes a goal for the engine, the host is the piece in the way, not the container.

Shutdown

Thirty seconds sits between a hung service and your GPU teardown

ShutdownTimeout defaults to thirty seconds. A background service that will not stop holds up StopAsync, and the provider is only disposed afterwards. Graphics objects are released last. Shorten it through HostOptions if you add hosted services that touch the network or the file system.

Scopes

The scope model is shaped for requests

A game has frame, scene and level lifetimes. A scope per level is reasonable. A scope per frame allocates a tracking list and a provider every frame, which is exactly the kind of steady garbage you spend the rest of the engine avoiding.

Habits

Nothing here costs frame time until you invite it in

The host adds no per-frame work by itself. What it adds is easy access to things that do: ILogger calls in hot paths without the source-generated message helpers, an options monitor spinning a file system watcher, and resolution from the container inside the loop instead of once at startup. The console logging provider also runs its own queue thread.

The middle path

There is an option between the two you have tried, and for a game it is probably the right one. Keep the built-in container, skip the host entirely, and state the validation options directly. This is also, finally, a clean answer to where startup validation lives.

Composition root, no hosting

Win32Application.Initialize("CapriKit.Tests.Tool", options);

var services = new ServiceCollection();
services.AddLogging(b => b.AddDebug());
services.AddSingleton(Win32Application.Window);
// snip: the rest of the registrations

await using var provider = services.BuildServiceProvider(new ServiceProviderOptions
{
    ValidateOnBuild = true,
    ValidateScopes = true,
});

var loop = provider.GetRequiredService<GameLoop>();
// snip: pump, update, render
Keeps

Everything that was actually bothering you

  • Validation at build, not at first resolve, and not conditional on an environment variable.
  • Reverse creation order disposal, reached through await using with no cast.
  • Scope validation, which the third-party adapter never implemented.
  • ILogger<T> injection, since AddLogging stands alone.
Gives up

The parts a game does not use

  • Layered configuration and IOptions<T> binding.
  • IHostedService and its start and stop ordering.
  • IHostApplicationLifetime as a shared shutdown signal.
  • Seven or so assemblies you were not going to call.

Note what happened on the way here. Dropping the third-party container is what made ValidateOnBuild reachable at all, because it is read by the default provider factory and by nothing else. That is a real argument for the built-in container that has nothing to do with speed or features.

Recommended shape

  1. Tool

    Keep the host in CapriKit.Tests.Tool

    Asset watching and shader recompilation are exactly what IHostedService is for, and configuration replaces the empty strings currently passed to the asset pipeline. Fix the six items above, state the validation options rather than relying on the environment, and bridge the message pump to IHostApplicationLifetime.

  2. Engine

    Assume the middle path for anything shipped

    A collection, a provider built with both validations on, and an explicit shutdown sequence for the graphics objects. No hosting dependency, no environment-dependent behavior, no reflection you would have to unpick later.

  3. Library

    CapriKit packages stay on the abstractions

    Ship IServiceCollection extensions like the existing asset pipeline registration and nothing more. That is what keeps every option on this page open for whoever consumes the package.
